## E. Security fix, its own build (C2, found 2026-10-31)
Restore the original signature and downgrade logic in `services.jar` (`PackageManagerServiceUtils`: `verifySignatures`, `compareSignatures`, `checkDowngrade` x3, `isDowngradePermitted`, `matchSignaturesCompat`, `matchSignatureInSystem`), taking the method bodies from the matching AOSP code (the Xiaomi 17 reference is a newer build, so only the logic, not the text, can be reused). Risk: any preinstalled app whose signing key differs from what the package database holds would stop installing or updating, and a wrong patch can stop the system booting, so: system partition build with a ready rollback, boot test, then check every priv-app (`tools/privcheck.py`), updates of Play Store, GMS and the camera/PhotoStage app, and an install of a differently signed APK that must now fail. `framework.jar` has the same kind of patch, worse: seven checks in `ApkSignatureSchemeV2Verifier`, `V3`, `V4` and `ApkSigningBlockUtils` call `com.xBuild.isOne()` (always true) where the original code calls `Signature.verify(...)` or `MessageDigest.isEqual(...)`; restore them too, and remove the `com.xBuild` helper once nothing uses it. **Dependency check done (read-only, 2026-10-31, `tools/re/ApkVerifyAll.java` over the 404 APKs of the shipped images):** 385 verify correctly; **12 fail** because they were modified after signing, so they only load because the checks are off: `MiuiSystemUI` (v1 signature references missing), `Settings`, `PowerKeeper`, `Joyose`, `MIUISystemUIPlugin`, `Phonesky` (Play Store), `HTMLViewer`, and the five overlays `AospFrameworkResOverlay`, `DevicesAndroidOverlay`, `DevicesOverlay`, `MiuiFrameworkTelephonyResOverlay`, `MiuiHomeLauncherResOverlay` (all `V3_SIG_APK_DIGEST_DID_NOT_VERIFY`). Restoring the checks everywhere would stop these from loading and the phone would not boot to a usable system. The camera (v15, debug key) and PhotoStage verify fine. `mi_ext` Dialer, Calendar, messaging, Contacts and the Mtk apps are 0-byte placeholders, and the GPU driver APK only failed in my checker (old JDK has no RSA-PSS).
**Built offline, not applied (2026-10-31):** `tools/re/fix_framework_signatures.py <framework.jar> <workdir> <out.jar>` restores the seven checks (each patched method is otherwise identical to the reference, so each fix is one instruction with the reference's registers), adds `com.xBuild.isSystemPath(String)` and makes `ParsingPackageUtils.getSigningDetails(...)` skip verification only for paths under `/system`, `/system_ext`, `/product`, `/vendor`, `/odm`, `/mi_ext` (and never when the path contains `..`). Checked by disassembling the result: the only changes in the three rebuilt dex files are those instructions, and no code is lost. **Still to do before a flash:** the matching `services.jar` patch (six methods), a bytecode-verifier run of both jars on the phone with `dex2oat` into `/data/local/tmp`, the build integration (the boot image is rebuilt on `/data` after a framework change, so the first boot is slow), and the tests listed above.
**`services.jar` half built offline too (2026-10-31):** `tools/re/fix_services_signatures.py <port services.jar> <reference services.jar> <workdir> <out>` restores **16** methods from the reference (same signatures, all 122 members they use exist in the port; rebuilt bodies are identical to the reference, no other method or class changed): in `PackageManagerServiceUtils` `verifySignatures`, `compareSignatures`, `checkDowngrade` (3), `isDowngradePermitted`, `matchSignaturesCompat`, `matchSignaturesRecover`, `matchSignatureInSystem`; `InstallPackageHelper.doesSignatureMatchForPermissions` (signature match for permission definitions was always true); `KeySetManagerService.shouldCheckUpgradeKeySetLocked` and `checkUpgradeKeySetLocked`; `ScanPackageUtils.assertMinSignatureSchemeIsValid` (old v1-only signatures were accepted for any target SDK); and the install-time package-verifier hooks in `VerifyingSession` (`isVerificationEnabled`, `isAdbVerificationEnabled` and `sendApkVerificationRequest` were no-ops, so Play Protect's pre-install check never ran). Found by scanning every method that is a stub in the port but long in the reference (14 hits; `PackageAbiHelperImpl.maybeThrowExceptionForMultiArchCopy` is a 64-bit related stub and was left alone).
**Special case:** `MiuiSystemUI` (target SDK 37) is the only preinstalled APK without a v2 or v3 signing block, so the restored minimum-scheme check would refuse it. The tool makes that one check return early for APKs under the system partitions, using the same `com.xBuild.isSystemPath` helper, **so the patched `services.jar` only works together with the patched `framework.jar` (a missing helper would crash at boot): always ship both.**
**ART bytecode verification done on the phone (2026-10-31, `tools/re/dex2oat_verify_on_phone.sh`; test files removed afterwards, nothing installed):** the patched `framework.jar` gives exactly the same class statuses as the original (38,236 Verified, 316 VerifiedNeedsAccessChecks, 48 Resolved, 10 NotReady in both). The patched `services.jar` together with the patched framework also matches the original (23,565 Verified, 61 VerifiedNeedsAccessChecks, 80 NotReady, 9 Resolved) and all five changed classes are Verified. Control: the patched `services.jar` with the original framework moves `ScanPackageUtils` to VerifiedNeedsAccessChecks (it cannot resolve `xBuild.isSystemPath`), which confirms the two files must ship together. What this does not prove: behaviour at run time, which needs the flash and the tests below.

**System image built offline (2026-10-31): `secure_build/out_sigfix/system.img`, plan, flash steps, tests and rollback in `docs/SIGFIX_FLASH_PLAN.md`; it also contains the Telecom speaker fix (F).**
**Risks to test:** the camera app is re-signed with a debug key, so signature permissions that Xiaomi apps define for each other (Gallery, Security) may now be refused; install-time verification may add a delay for sideloaded apps; packages installed during the bypass era must still match their stored certificates (check on a copy of `packages.xml` before flashing).
**Toolchain pitfall found:** the old `tools/re/Smali.java` loaded dex files with `Opcodes.getDefault()`, which misreads `invoke-polymorphic` (used by `RemoteViews` and `CursorWindow`) as an odex opcode and the assembler then silently drops it. It now uses API 34. After any disassemble and reassemble, diff the smali of the original and the rebuilt dex and check there is no `#disallowed odex opcode`.
**Design that keeps those apps working and closes the hole:** enforce the real checks for every APK that is not on a read-only system partition (anything installed, updated or sideloaded under `/data`, including updates of these same apps), and skip only for APKs located under `/system`, `/system_ext`, `/product`, `/vendor`, `/odm`, `/mi_ext`. Those partitions are part of the signed-and-hashed OS image (EROFS with dm-verity), so they're as trusted as the framework itself. In `services.jar` the cached certificates of these modified apps are still the original Xiaomi ones, so the restored `compareSignatures` and `verifySignatures` keep matching for them. Alternative, bigger: put back the stock versions of the 12 apps (loses the porter's patches) or re-sign them (needs the platform key we don't have). Needs the owner's decision and a flash; goes after the camera shots are analysed.

## F. Telecom fix: loudspeaker button sometimes does nothing (found 2026-10-31)
Cause and evidence: `docs/hardware/subsystems/CALL_SPEAKER_BUG.md`. Telecom keeps a stale cached communication device after another app used the speaker, then skips switching to the speaker. Fix: patch `isCurrentCommunicationDevice` in `/system/priv-app/Telecom/Telecom.apk` to read the real device from `AudioManager` (as the Xiaomi 17 reference does). System partition build with rollback; test with a WhatsApp speaker call followed by a phone call. Workaround until then: tap Speaker off and on.
