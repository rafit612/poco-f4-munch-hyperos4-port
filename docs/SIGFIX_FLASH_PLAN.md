## RESULT of the first flash (2026-10-31 20:53): did NOT boot, rolled back at 21:07
`out_sigfix/system.img` (all three fixes together) was flashed no-wipe. The phone never came up on adb for 12 minutes and then dropped into the bootloader (slot A: `slot-successful` yes, retry count down to 2, `is-userspace` no), so the boot failed early, before `adbd`. No log of the failed boot exists (no pstore, adb never appeared). Rollback with `flash_system_nowipe.sh out_tele_T20261030_v13` worked: boot completed in about 1 min, the system partition hash is back to `a66cc607...`, SELinux enforcing, user data untouched.
Cause: **unknown**. Candidates, not tested: (1) the system image carries fs-verity metadata (`*.fsv_meta`) per file, and the three replaced files kept their old `.fsv_meta`; (2) dex version 040 written by smali in the boot-classpath `framework.jar` (the original is 039); (3) the old boot image and odrefresh artifacts on `/data` built against the old `framework.jar`; (4) a fix that really broke a boot-critical app (the exemption path check or an unexpected signature use). The two-file and one-file variants were not tried separately.
**Next step proposal:** bisect, one flash each with rollback ready: (a) `Telecom.apk` alone (also delivers the speaker fix; low risk), (b) `framework.jar` alone with dex version 039 and matching `.fsv_meta` handling, (c) `services.jar`. Before that, check how `*.fsv_meta` is used at boot, and try to capture an early log (kernel console is not available; consider `logcat` over adb at the first moment, or a debug `init` log).

## RESULT of bisect step 1 (2026-10-31 21:16): Telecom-only image ALSO did not boot, rolled back at 21:23
`secure_build/out_telecom/system.img` (sha256 35980b9f..., the running image with only `Telecom.apk` replaced; 1 file replaced, 0 removed, 0 errors) behaved exactly like the first image: no adb, fell to the bootloader after about 5 minutes. Rollback worked again (system hash a66cc607..., boot in 1 min). **So the cause is not in the framework or services patches.**
What is known: EROFS superblock fields of the rebuilt image equal those of the running image (same features, same file statistics; only build time, UUID and size differ; the Telecom image is 8,192 bytes larger than the partition's 910,880,768 bytes, the first image 5.9 MB smaller, so size does not explain both). The patched `Telecom.apk` fails its own v3 digest (CHUNKED_SHA256), the same kind of mismatch as the 12 modified system apps that boot fine, because the running framework skips that check.
Remaining suspects: (a) **the rebuild path itself for the system partition** (the running `system.img` equals `out_tele_T20261026_prev`; a re-tar of it may lose something that `verify_img` does not compare, for example the exact partition-size padding, inode flags or dir timestamps); (b) the Telecom replacement (a bad zip or the changed digest hitting a path I did not see).
**Next control (one flash, rollback ready):** rebuild the system image from the running one with **no payload at all** and flash it. If it boots, the Telecom file is the problem; if it fails, the rebuild path is. Alternative without a flash: patch the three files directly inside the original image bytes where sizes allow (not possible, EROFS is compressed), or flash only after matching the original image's exact size by padding.

## UPDATE 2026-10-31 night: the real cause of the failed boots, and the state now on the phone
**Cause of the three failed boots (sigfix, telecom-only, null rebuild): my build setup, not the patches.** I had made `W/port/system` a symlink to the mounted base image, so `erofs_tar_rebuild.py` read the symlink's own attributes as the image root: the rebuilt `/` had mode 0777, owner `system` (uid 1000) and no SELinux label (original: 0755, root, `u:object_r:rootfs:s0`). The system partition is system-as-root, so every such image died in early boot. The no-change rebuild reproduced it. `verify_img.py` never compared the root entry. Fixes: build with the image really mounted at `W/port/system`; `build_tele.sh` now refuses a symlink and checks that the new image's root equals the original's; the full comparison script (all entries, modes, owners, xattrs, content hashes) is the acceptance test before any flash.
**Run on the phone since (all flashed no-wipe, rollback = `out_tele_T20261030_v13`):**
- `out_sigfix2` (framework: 7 verifier checks + system-path exemption; services: 16 methods; Telecom speaker fix): **boots in about a minute, currently installed.** Tests: tampered APK refused (`INSTALL_PARSE_FAILED_NO_CERTIFICATES ... SHA-256 digest of contents did not verify`); same-key update works; downgrade refused (`INSTALL_FAILED_VERSION_DOWNGRADE`); 486 packages, 99 user apps, no fatal exceptions, no signature errors in the log. **Still failing: an update signed with a different key is accepted** (`SigningDetails.checkCapability` and friends are still stubbed to `true` in the framework), so the most important part of C2 is not fixed yet.
- `out_sigfix3` (adds the restoration of `SigningDetails.checkCapability`/`checkCapabilityRecover`/`hasAncestorOrSelf`/`hasCommonAncestor` and `ApkSigningBlockUtils.verifyIntegrityForVerityBasedAlgorithm`, tool step 4): **zygote crash loop at boot**, rolled back to sigfix2. Log: `IllegalStateException: Signature mismatch on system package com.qti.phone for shared user android.uid.qtiphone` from `ReconcilePackageUtils.reconcilePackages`. With real checks, system apps that share a user id but were signed by different keys (the port mixes apps from different builds) are refused. The stubs were hiding this.
**What is left for the different-key fix:** exemptions for packages on the read-only system partitions at the call sites in `services.jar` that use `checkCapability` (shared-user join in `ReconcilePackageUtils`, `verifySignatures`, `doesSignatureMatchForPermissions`, key-set checks), then boot again; `adb` works while zygote loops, so each iteration produces a log. System apps that define or use signature permissions with different certificates may lose permissions even if boot works, so test camera, calls, Gallery, Security, PowerKeeper.
**Not yet tested on sigfix2:** the call-speaker fix (needs the owner: WhatsApp speaker call, end it, phone call, tap Speaker), camera and PhotoStage, calls on both SIMs, Bluetooth audio.

## If a preinstalled app is refused after the flash
Most likely cause: an app that was modified after signing and sits outside the six exempt partitions, or a signature permission between apps with different certificates (the camera is signed with a debug key). The log line names the package. Remedy options: roll back, or add that path/package to the exemption list in `com.xBuild.isSystemPath` and rebuild.
